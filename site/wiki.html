wiki/data-compression.md

資料壓縮（Data compression）

💡 一句話：用比原本更少的位元（bit）來表示同一份資訊。

定義

  • 資料壓縮又稱為信源編碼（source coding），是用比原始表示法更少的位元來編碼資訊。01·Lead
  • 負責壓縮的叫編碼器（encoder），負責還原的叫解碼器（decoder）。01·Lead
  • 壓縮分成兩大類：無失真（lossless）與失真（lossy），差別見 無失真 vs 失真壓縮（Lossless vs Lossy）。01·Lead

歷史脈絡

  • 熵編碼（entropy coding）起源於 1940s 的 Shannon–Fano 編碼，它是 Huffman 編碼（Huffman coding） 的基礎。01·Theory

  • 算術編碼（Arithmetic coding）（算術編碼）是較現代的技術，壓縮效果可以比 Huffman 編碼更好，也適合統計特性會隨時間變化的「自適應模型」。01·Theory

  • 壓縮能壓到多小，極限由「熵」決定，見 熵（Entropy）。02·Data compression

相關：無失真 vs 失真壓縮（Lossless vs Lossy）、熵（Entropy）

wiki/lossless-vs-lossy.md

無失真 vs 失真壓縮（Lossless vs Lossy）

💡 比喻：無失真像把衣服真空壓縮，打開後一模一樣；失真像把照片縮小，看起來差不多但細節回不來。

無失真壓縮（lossless）

  • 原理是移除「統計上的冗餘」，因此原始資料可以完整還原。01·Lossless
  • 原文：「No information is lost in lossless compression.」01·Lossless
  • 最簡單的例子是連續長度編碼（run-length encoding）：把一長串相同顏色的像素，改記成「個數＋顏色」。01·Lossless
  • 最常用的方法之一是 Lempel–Ziv 家族，包括 LZW 和 DEFLATE。01·Lossless

失真壓縮（lossy）

  • 丟掉被判斷為不必要或較不重要的資訊，用一些保真度換取更小的檔案。01·Lossy

  • 例：人眼對亮度比對顏色敏感，所以 JPEG 會捨去觀看者不易察覺的細節。01·Lossy

  • 本 wiki 的主角 Huffman 與算術編碼都用於無失真壓縮。05·Lead 06·Lead

相關：資料壓縮（Data compression）

wiki/entropy.md

熵（Entropy）

💡 一句話：熵＝「平均有多意外」；越難猜的資料，熵越高，越難壓縮。

定義與直覺

  • 隨機變數的熵，衡量其可能結果的平均不確定性（或資訊量）。02·Lead
  • 熵由 Claude Shannon 在 1948 年的論文提出，所以又稱 Shannon 熵。02·Lead
  • 對數的底決定單位：底 2 的單位是位元（bit）。02·Lead
  • 越可能發生的事帶來的資訊越少，越不可能的事帶來的資訊越多；例如「這張彩券不會中」幾乎沒告訴你什麼。02·Introduction
  • 每個事件的「意外程度」稱為自資訊（self-information），熵就是自資訊的期望值。02·Introduction

例子：擲硬幣

  • 公平硬幣（p = 1/2）最難猜，熵是 1 bit（one bit）。02·Example
  • 永遠出同一面的硬幣沒有不確定性，熵是零（zero）。02·Example
  • 擲骰子的熵比擲硬幣高，因為每個結果更不可能。02·Example

和壓縮的關係

  • 資訊理論可以算出傳達一則訊息「最少需要多少資訊」，這正是資料壓縮的核心。02·Data compression
  • 四個字母 A、B、C、D 機率相同時，每個字母需要兩個 bits（two bits）；機率不均時，用長短不一的碼就能平均更少。02·Data compression
  • 英文文字的熵約為每字元 0.6 到 1.3 bits，所以英文很好壓縮。02·Data compression
  • 熵是無失真壓縮的極限，這就是 信源編碼定理（Shannon's source coding theorem）。02·Data compression

wiki/source-coding-theorem.md

信源編碼定理（Shannon's source coding theorem）

💡 一句話：熵是一道「地板」——無失真壓縮可以很接近它，但壓到它下面一定會掉資訊。

內容

  • 又稱無雜訊編碼定理（noiseless coding theorem），它訂出了資料壓縮在統計上的極限。03·Introduction
  • 適用對象：每個符號彼此獨立、同分布（i.i.d.）的資料來源。03·Introduction
  • 壓到低於熵，幾乎一定會遺失資訊；但可以做到「任意接近熵」而幾乎不遺失。03·Introduction
  • 白話版：N 個符號、每個的熵是 H，只要給「多於 N×H 個 bits」就能在 N 很大時幾乎無損壓縮。03·Statements
  • 對「一個符號換一個碼字」的符號碼（symbol code），定理同時給出平均碼長的上界與下界。03·Statements

為什麼重要

  • 這個定理讓 熵（Entropy） 從抽象的「不確定性」變成有實際意義的「最少要用幾個 bits」。03·Introduction 💡 後面介紹的編碼方法，都可以拿「離熵多近」來評分。

相關：熵（Entropy）、資料壓縮（Data compression）、Shannon–Fano 編碼（Shannon–Fano coding）

wiki/prefix-code.md

前綴碼（Prefix code）

💡 一句話：沒有任何一個碼字是另一個碼字的「開頭」，所以一串 0/1 從頭讀下去，永遠只有一種切法。

定義

  • 前綴碼：沒有任何碼字（codeword）是另一個碼字的前綴，所以解碼不會有歧義。05·Terminology
  • 「Huffman code」這個詞常被寬鬆地拿來指任何前綴碼，即使不是用 Huffman 演算法做出來的。05·Terminology

💡 例子：若 A=0、B=10、C=11，收到 01011 只能切成 0｜10｜11 → A B C。反例：若 A=0、B=01，收到 01 就不知道是「B」還是「A＋下一個碼的開頭」。

怎麼評分一套前綴碼

  • 加權路徑長度（weighted path length）＝每個符號的權重 × 碼長，再全部加總；把它壓到最小，就等於把平均碼長壓到最小。05·Terminology
  • 平均碼長的理論下限就是 熵（Entropy）。05·Terminology

相關：Shannon–Fano 編碼（Shannon–Fano coding）、Huffman 編碼（Huffman coding）、熵（Entropy）

wiki/shannon-fano.md

Shannon–Fano 編碼（Shannon–Fano coding）

💡 一句話：「由上往下對半切」——把符號依機率排好，切成兩堆差不多重的，左邊給 0、右邊給 1，一直切到每堆只剩一個。

是什麼

  • 以 Claude Shannon 和 Robert Fano 命名，用符號的機率建出一套前綴碼（prefix code）。04·Introduction
  • 其實有兩種不同演算法共用這個名字：Shannon 的方法（1948）和 Fano 的方法（1949）。04·Naming
  • 它們產生的碼「不一定最好」：平均碼長與最佳值相差在一個 bit 以內（within one bit），但不保證最短；Huffman 編碼才保證。04·Introduction

Fano 的做法（由上而下）

  • 把符號依機率由大到小排序，切成兩組、讓兩組總機率盡量接近；第一組加「0」、第二組加「1」，再對每組重複，直到每個符號單獨一組。04·Fano's code

同一個例子：五個符號 A–E

符號 次數（共 39） 04·Fano's code 機率 Fano 碼長 Huffman 碼長
A 15 0.385 2 1 04·Fano's code 04·Comparison with Huffman coding
B 7 0.179 2 3 04·Fano's code 04·Comparison with Huffman coding
C 6 0.154 2 3 04·Fano's code 04·Comparison with Huffman coding
D 6 0.154 3 3 04·Fano's code 04·Comparison with Huffman coding
E 5 0.128 3 3 04·Fano's code 04·Comparison with Huffman coding
  • 第一刀切在 B 和 C 之間，兩邊總次數是 22 和 17。04·Fano's code
  • Fano 平均碼長約 2.28 bits；Shannon 的方法是 2.62 bits。04·Comparison with Huffman coding
  • Huffman 平均碼長約 2.23 bits，三者中最短。計算值

wiki/huffman-coding.md

Huffman 編碼（Huffman coding）

💡 一句話：「由下往上合併」——每次把最不常出現的兩個符號綁在一起，綁到剩一棵樹；常出現的符號離樹根近，碼就短。

是什麼

  • Huffman 碼是一種用於無失真壓縮的「最佳」前綴碼（Prefix code）：越常出現的符號，給越短的位元串。05·Lead
  • 由 David A. Huffman 在 MIT 讀博士（Sc.D.）時提出，1952 年發表。05·Lead

故事：一份期末報告

  • 1951 年 Huffman 修 Robert M. Fano 的資訊理論課，老師讓學生在「期末報告」和「期末考」二選一，他選了報告，題目是找出最有效率的二進位碼。05·History
  • 他原本一直證明不出哪套碼最好，直到想到「依頻率排序建二元樹」的方法，並證明它最有效率。05·History
  • 和由上而下的 Shannon–Fano 編碼（Shannon–Fano coding） 不同，由下而上建樹保證最佳。05·History
  • ⚠ 矛盾：Huffman 編碼的年代，Wikipedia〈Huffman coding〉說 1951 年修課時提出、1952 年發表 05·History 05·Lead；〈Data compression〉則寫「developed in 1950」01·Theory。

演算法三步驟

  • ① 建樹：每個符號先是一片葉子，權重＝出現頻率；反覆把「權重最小的兩個節點」合併成一個新節點（權重相加），直到只剩一個根。05·Basic technique
  • ② 產生碼字：從根往下走，左邊標 0、右邊標 1；走到某片葉子的路徑就是那個符號的碼。05·Basic technique
  • ③ 解碼：一個一個讀 bit、沿著樹往下走，走到葉子就輸出一個符號；所以解碼端必須拿到同一棵樹或頻率表。05·Basic technique

例子：五個符號 a–e

符號 權重 碼字 碼長 05·Example
a 0.10 010 3 05·Example
b 0.15 011 3 05·Example
c 0.30 11 2 05·Example
d 0.16 00 2 05·Example
e 0.29 10 2 05·Example
  • 平均碼長 2.25 bits／符號，熵約 2.205 bits，已非常接近理論極限。05·Example

什麼時候最好、什麼時候不夠好

  • 在「機率已知、符號彼此獨立、一次編一個符號」的條件下，Huffman 是最佳的。05·Optimality
  • 機率剛好是 1/2 的次方時效率最高；符號種類很少時，浪費可能很明顯。05·Optimality
  • 把多個符號綁成一塊（blocking）可以改善，但成本會指數成長。05·Optimality
  • 算術編碼能更貼近真實機率，但 Huffman 比較快，歷史上也沒有專利問題。05·Optimality

實際應用

  • 前綴碼常被當作壓縮流程的最後一段，例如 DEFLATE（PKZIP、gzip 使用）、JPEG、MP3。05·Applications
  • 傳真機使用修改版的 Huffman 編碼。05·Applications

算術編碼（Arithmetic coding）

💡 一句話：不幫每個符號各發一個碼，而是把「整則訊息」縮成 0 到 1 之間的一個小數。

是什麼

  • 算術編碼是一種用於無失真壓縮的熵編碼方法。06·Lead
  • 它不是把每個符號換成各自的碼，而是把整則訊息編成一個小數 q，0 ≤ q < 1。06·Lead
  • 最好的成績由來源的熵決定，而算術編碼能很接近這個極限，訊息越長越明顯。06·Lead

核心想法：不斷切區間

  • 先要有一個「模型」預測每個符號的機率；編碼器從區間 [0, 1) 開始，依機率切成小段，留下實際符號對應的那一段，再重複。06·Defining a model
  • 範例模型：NEUTRAL 60%、POSITIVE 20%、NEGATIVE 10%、END-OF-DATA 10%；END-OF-DATA 表示訊息結束。06·Defining a model
  • 編碼「NEUTRAL → NEGATIVE → END-OF-DATA」時，區間依序縮成 [0, 0.6) → [0.48, 0.54) → [0.534, 0.54)。計算值 06·Defining a model
  • 來源的解碼範例：小數 0.538 依序解出 NEUTRAL、NEGATIVE、END-OF-DATA。06·Decoding example
  • 只要傳「足夠落在最終區間內」的位數就好；解碼端必須使用和編碼端相同的模型。06·Decoding example

💡 直覺：常見的符號佔的區間寬，切完區間縮得少，花的位數就少；罕見符號讓區間縮很多，花的位數就多。

實作上的眉角

  • 真實的編碼器沒辦法記住無限精度的小數，所以用固定精度並把邊界四捨五入。06·Precision and renormalization
  • 重新正規化（renormalization）：當區間上下界的開頭幾位數相同時，就先把那幾位輸出、把區間放大，才能一直編下去。06·Precision and renormalization

歷史

  • 基本演算法由 IBM 的 Jorma Rissanen 和 Stanford 博士生 Richard Pasco 各自獨立提出，兩人都在 1976 年五月（May 1976）發表。06·History and patents
  • 許多相關技術曾被申請專利，現在大多已過期；專利顧慮曾讓 bzip2 放棄算術編碼，JPEG 實作也多半改用 Huffman。06·History and patents

Huffman vs 算術編碼（比較頁）

💡 一句話：Huffman 每個符號只能用「整數個」bit；算術編碼等於可以用「零點幾個」bit，所以更貼近熵。

關鍵差別：整數位元的限制

  • Huffman 給每個符號的碼長都是整數個 bit，這限制了它的效率。06·Huffman coding
  • 極端例子：兩個符號、機率 0.95 和 0.05 時，單純的 Huffman 完全壓不了，每個符號還是要一個 bit（one bit）。06·Huffman coding
  • 只有機率剛好是二的次方（powers of two）時，Huffman 才會達到熵。06·Huffman coding
  • 把符號綁成一塊可以改善，但要接近熵，塊會變得非常大；算術編碼不需要付這個代價就能逼近熵。06·Huffman coding

兩個來源的一致結論

  • 〈Data compression〉：算術編碼能比知名的 Huffman 演算法壓得更好。01·Lossless
  • 〈Huffman coding〉：Huffman 在「一次編一個符號」的方法中最佳，但需要時算術編碼能壓得更好。05·Lead

💡 那為什麼 Huffman 還到處都是？因為快、簡單、沒有專利包袱——工程上「夠好又便宜」常常贏過「最好但貴」。

Data compression（Wikipedia）

  • URL: https://en.wikipedia.org/wiki/Data_compression
  • 擷取日期：2026-11-12
  • 擷取方式：WebFetch 工具。該工具因著作權限制不提供全文，回傳「重點摘要＋125 字元內短引文」。引號內為原文短引，其餘為擷取工具的英文摘要。

Lead

Data compression (also called source coding or bit-rate reduction) encodes information using fewer bits than the original representation. Compression is either lossy or lossless. The device that compresses is an encoder, and the one that reverses the process is a decoder.

Lossless

Lossless methods remove statistical redundancy so that the original data can be fully restored. "No information is lost in lossless compression." Run-length encoding, which replaces long runs of identical pixels with a count and a color, is a simple example. Lempel–Ziv methods, including LZW and DEFLATE, are among the most widely used. The strongest modern lossless compressors rely on probabilistic models, and arithmetic coding can combine with those models to outperform Huffman coding. Quote: "It can achieve superior compression compared to other techniques, such as the better-known Huffman algorithm."

Lossy

Lossy compression discards information judged unnecessary or less important. It trades some fidelity for smaller size, and the right balance depends on how people perceive the data. For example, human eyes are more sensitive to brightness than to color, so image formats such as JPEG round off detail that viewers are unlikely to notice.

Theory

Entropy coding "originated in the 1940s with the introduction of Shannon–Fano coding", which was "the basis for Huffman coding which was developed in 1950." Arithmetic coding is a more modern technique that uses a finite-state machine to turn a series of input symbols into a bit string. It can compress better than Huffman coding and works well with adaptive models whose statistics change over time.

raw/02-entropy.md（唯讀）

Entropy (information theory)（Wikipedia）

  • URL: https://en.wikipedia.org/wiki/Entropy_(information_theory)
  • 擷取日期：2026-11-12
  • 擷取方式：WebFetch 工具（重點摘要＋125 字元內短引文；引號內為原文）。

Lead

"the entropy of a random variable quantifies the average level of uncertainty or information" associated with its possible outcomes. Entropy measures the expected amount of information needed to describe the variable's state, given how probability is spread across its possible states. The logarithm base sets the unit: base 2 gives bits, base e gives nats, and base 10 gives hartleys. Claude Shannon introduced the concept in his 1948 paper, which is why it is also called Shannon entropy.

Introduction

"the \"informational value\" of a communicated message depends on the degree to which the content" is surprising. Likely events convey little information, while unlikely events convey a lot. A lottery ticket that will not win tells you almost nothing, but knowing a specific number will win is highly informative. Surprisal, or self-information, increases as an event's probability decreases, and entropy is the expected value of that surprisal.

Example

"Consider a coin with probability p of landing on heads and probability 1 − p of landing on tails." A fair coin (p = 1/2) gives the maximum surprise and an entropy of one bit. A coin that always lands the same way has zero entropy, because there is no uncertainty. Biased coins fall between these extremes. A die roll has higher entropy than a coin toss, since each die outcome is less probable.

Data compression

"Information theory is useful to calculate the smallest amount of information required to convey a message", which is central to data compression. A four-letter example (A, B, C, D): equal probabilities need two bits per letter, but skewed probabilities allow variable-length codes that average fewer bits. Shannon's source coding theorem sets entropy as the limit on lossless compression. "English text has between 0.6 and 1.3 bits of entropy per character of the message." English is fairly predictable, so it compresses well. The PPM algorithm can reach about 1.5 bits per character on English text.

Shannon's source coding theorem（Wikipedia）

  • URL: https://en.wikipedia.org/wiki/Shannon%27s_source_coding_theorem
  • 擷取日期：2026-11-12
  • 擷取方式：WebFetch 工具（重點摘要＋125 字元內短引文；引號內為原文）。

Introduction

Shannon's source coding theorem, also called the noiseless coding theorem, sets "the statistical limits to possible data compression." It applies to data from a source of independent, identically distributed (i.i.d.) random variables and gives operational meaning to Shannon entropy. Compressing such data below its entropy rate almost certainly loses information, while rates arbitrarily close to the entropy are achievable with negligible loss. For sources with more complex dependencies, Kolmogorov complexity is a better tool for describing compression limits.

Statements

Source coding (informal): N i.i.d. random variables, each with entropy H(X), "can be compressed into more than N H(X)" bits with negligible risk of information loss as N grows; compressing them into fewer bits almost certainly loses information. Symbol codes (informal): the theorem "places an upper and a lower bound on the minimal possible expected length of codewords", as a function of the entropy of the input and the size of the target alphabet.

Shannon–Fano coding（Wikipedia）

  • URL: https://en.wikipedia.org/wiki/Shannon%E2%80%93Fano_coding
  • 擷取日期：2026-11-12
  • 擷取方式：WebFetch 工具（重點摘要；不提供全文）。
  • ⚠ 擷取註記：Huffman 比較段的平均碼長，原頁數字未成功渲染，擷取工具回報的「about 2.23 bits」是工具自行計算的，不是來源數字，故本檔不收錄該值。

Introduction

Shannon–Fano coding is one of two related techniques, named after Claude Shannon and Robert Fano, for building a prefix code from a set of symbols and their probabilities. Both methods produce suboptimal prefix codes. Their expected codeword lengths are within one bit of the optimum, but they don't always reach the lowest possible length. Huffman coding does.

Naming

Two different algorithms share the name. Shannon's method (1948) chooses codeword lengths from the symbol probabilities and then assigns codewords using cumulative probabilities. Fano's method (1949) recursively splits the sorted symbols into two groups of nearly equal probability and appends a bit at each split. Some authors call Shannon's method "Shannon coding" and Fano's method "Fano coding" to avoid the confusion.

Fano's code

Fano's method sorts symbols from most to least probable and divides them into two sets with nearly equal total probability. The first set receives a "0" and the second a "1." Each set with more than one symbol is then split the same way until every symbol is alone, and its codeword is the sequence of bits recording its splits. Example: Five symbols A–E have counts of 15, 7, 6, 6, and 5 out of 39 total observations, giving probabilities of 0.385, 0.179, 0.154, 0.154, and 0.128. The split between B and C gives totals of 22 and 17. Further splits produce codewords of 2 bits for A, B, and C and 3 bits for D and E. The resulting average length is about 2.28 bits.

Comparison with Huffman coding

Huffman coding builds its tree from the leaves up by repeatedly merging the two least probable nodes, so it always yields an optimal prefix code for the given probabilities. Example: Using the same five symbols, Huffman coding gives A a 1-bit codeword and B, C, D, and E 3-bit codewords. This beats Fano's 2.28 bits and Shannon's 2.62 bits.

raw/05-huffman-coding.md（唯讀）

Huffman coding（Wikipedia）

  • URL: https://en.wikipedia.org/wiki/Huffman_coding
  • 擷取日期：2026-11-12
  • 擷取方式：WebFetch 工具（重點摘要；不提供全文）。

Lead

A Huffman code is an optimal prefix code used for lossless data compression. David A. Huffman developed the algorithm as an MIT Sc.D. student and published it in 1952. It assigns shorter bit strings to more frequent symbols. Huffman coding is optimal among methods that encode symbols one at a time, but arithmetic coding can achieve better compression when that is needed.

History

In 1951, Huffman was a student in an information theory course taught by Robert M. Fano, who offered students a choice between a term paper and a final exam. Huffman chose the paper, on finding the most efficient binary code. He struggled to prove that any code was optimal until he developed the idea of building a frequency-sorted binary tree, which he then showed was most efficient. Unlike the top-down Shannon–Fano approach, building the tree bottom-up guarantees optimality.

Terminology

  • Prefix code: no codeword is a prefix of another, so decoding is unambiguous. "Huffman code" is often used loosely for any prefix code, even ones not built by Huffman's algorithm.
  • Weighted path length: the sum of each symbol's weight times its codeword length. Minimizing it minimizes the expected codeword length.
  • Entropy (Shannon): the theoretical lower limit on average bits per symbol.

Example

Five-symbol example (a–e):

Symbol Weight Codeword Length
a 0.10 010 3
b 0.15 011 3
c 0.30 11 2
d 0.16 00 2
e 0.29 10 2

The weighted average length is 2.25 bits per symbol, compared with an entropy of about 2.205 bits, so the code is very close to the theoretical limit.

Basic technique

Building the tree: each symbol starts as a leaf node weighted by its frequency. Repeatedly, the two lowest-weight nodes are merged under a new internal node whose weight is their sum, until one root node remains. A priority queue does this in O(n log n) time. Generating codes: traverse the tree from the root, labeling left edges 0 and right edges 1. A symbol's code is the sequence of labels on the path to its leaf. Decompression: read bits and walk the tree until reaching a leaf, which yields a symbol. The decoder needs the tree or frequency table, which can be preset or sent as a prefix to the data.

Optimality

Huffman coding is optimal among symbol-by-symbol codes when symbol probabilities are known and symbols are independent. It is not optimal when symbols are combined into blocks, when probabilities are unknown, or when symbols are not independent and identically distributed. It is most efficient when symbol probabilities are powers of 1/2. For small alphabets, its inefficiency can be significant. Blocking symbols can improve compression but grows exponentially in cost. Arithmetic coding can match the true probabilities more closely, but Huffman coding is faster and was historically free of patent issues.

Applications

Prefix codes are widely used as a back-end stage in compression, for example in DEFLATE (used in PKZIP and gzip), JPEG, and MP3. Fax machines use a modified Huffman scheme. Variants include adaptive Huffman coding, which updates the tree as data arrives.

raw/06-arithmetic-coding.md（唯讀）

Arithmetic coding（Wikipedia）

  • URL: https://en.wikipedia.org/wiki/Arithmetic_coding
  • 擷取日期：2026-11-12
  • 擷取方式：WebFetch 工具（重點摘要；不提供全文）。

Lead

Arithmetic coding is an entropy coding method for lossless compression. Instead of replacing each symbol with its own code, it encodes an entire message as a single number, a fraction q with 0 ≤ q < 1. Frequent symbols take fewer bits and rare ones take more, so the total size drops. The best possible result is set by the source's entropy, and arithmetic coding gets close to that limit, especially for long messages.

Equal probabilities

If each of three symbols (A, B, C) is equally likely, fixed-width binary codes need 2 bits per symbol, which wastes one bit pattern. Treating the sequence as a base-3 number and then converting it to binary uses fewer bits overall. The article's example encodes "ABBCAB" in 10 bits instead of 12. When all symbols are equally likely, no compression is possible beyond this.

Defining a model

A model predicts how likely each symbol is. The encoder starts with the interval [0, 1) and splits it into sub-intervals sized by those probabilities. It then keeps the sub-interval matching each actual symbol and repeats. Example model with four symbols: NEUTRAL (60%), POSITIVE (20%), NEGATIVE (10%), and END-OF-DATA (10%). The END-OF-DATA symbol marks where the stream stops.

Decoding example

The fraction 0.538 is decoded by repeatedly checking which sub-interval contains it. This recovers NEUTRAL, then NEGATIVE, then END-OF-DATA, which ends decoding. Only enough digits to land inside the final interval need to be transmitted. The decoder must use the same model as the encoder.

Precision and renormalization

Real coders cannot track exact fractions, so they work at fixed precision and round interval boundaries. Renormalization handles the limit on precision: when the current range shares leading digits, those digits are emitted and the range is shifted and widened. This lets the coder keep encoding long messages.

Huffman coding

Huffman coding gives each symbol a whole-number bit length, which limits its efficiency. For a binary source with probabilities 0.95 and 0.05, plain Huffman coding cannot compress at all, since each symbol still costs one bit. Grouping symbols into blocks improves this, and Huffman coding reaches entropy only when probabilities are powers of two. However, the blocks grow very large to get close to entropy. Arithmetic coding approaches entropy without this cost.

History and patents

Jorma Rissanen at IBM Research and Richard Pasco, a Stanford PhD student, independently developed the basic algorithms. Both published in May 1976. Many arithmetic coding techniques were patented over the years; those patents have mostly expired. Patent concerns led bzip2 to drop arithmetic coding, and JPEG implementations mostly use Huffman coding instead.

五件事（講義 p.20）
🎯 目標 只用 wiki/ 的內容，產出給「完全沒學過的同學」看的教學 HTML 簡報 topic-*/deck.html
🚧 限制 不得使用 wiki 以外的知識；每一關只能讀「上一關的產出」（見下表）；渲染不得改字
✅ 完成標準 所有程式檢查（G1–G4）全過＋AI 審查無「錯誤」級問題，產出 report.md
🛑 停止條件 ① 全過 → 交件；② 任一節點的小 loop 改滿上限（逐頁稿 2 輪、渲染 2 輪、全域 3 輪）→ 停下附報告交人處理；③ 檢索後相關頁 < 3 → 一開始就停
⏰ 觸發 使用者說「/topic-slides <主題>」；或 wiki 有新 ingest 後重跑

每一關只能看什麼、不能做什麼（講義 p.43）

節點 輸入（只能看） 輸出 不能做 檢查
① 檢索 wiki/*.md、主題關鍵字 sources.md 讀 raw、上網 G1：相關頁 ≥ 3、必備概念都有頁
② 證據卡 一個 wiki 頁 cards/<頁名>.md 混用其他頁、改寫句子 卡片每句必須與 wiki 原句完全相同（G2 內含）
③ 大綱 sources.md、cards/ outline.md 寫內文 👤 人工確認（教學順序、讀者程度）
④ 逐頁稿 outline.md＋該頁對應的卡 drafts/NN.md 引用卡片以外的內容 G2：每頁有出處、[card:] 存在、數字在所引卡片中、8–15 頁、每頁字數上限
AI 審查 逐頁稿＋所引卡片（新對話） checks/review-*.md 審自己的作品、動手改 忠實度（有沒有講反）、覆蓋率（必備概念）
⑤ 渲染 已通過的 drafts/ deck.html 改任何一個字（由腳本決定性渲染） G3：每頁無溢出、稿件每句都原樣出現在 HTML、互動元件數字可追溯

錯在哪一關就退回哪一關（講義 p.44）

  • 某頁講錯 → 只重寫那一頁（其他頁不動）
  • 卡片本身錯 → 退回 ② 重抽那一頁的卡
  • 字太多溢出 → 不硬塞、不縮字級，退回 ④ 縮短那一頁
  • 看大綱時發現缺主題 → 退回 ① 補檢索（wiki 沒有就要先 ingest 新來源）

每格裡面還是 loop（講義 p.45）

  • 逐頁稿節點：寫 → G2 → 修，最多 2 輪
  • 渲染節點：產生 HTML → 截圖＋溢出檢查 → 縮短稿 → 再渲染，最多 2 輪
